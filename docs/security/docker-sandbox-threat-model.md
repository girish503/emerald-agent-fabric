# Track E — Docker/OCI Sandbox Isolation & Execution Security Threat Model

## 1. Overview & Research Context

Emerald Agent Fabric provides governed execution for autonomous software-engineering agents. When an agent or task executes code, that code may be user-submitted, multi-tenant, or generated by an adversarial open-weight model.

The execution boundary must guarantee:
1. **Host Integrity**: Untrusted workloads cannot read, mutate, or escape into the host operating system or host filesystem.
2. **Tenant Confinement**: Workloads running on behalf of Tenant A cannot inspect, access, or disrupt the workspace, processes, or artifacts of Tenant B.
3. **Network Isolation**: Strict untrusted execution runs with `--network=none`. No external internet access, implicit DNS, or access to host localhost network services is permitted.
4. **Credential Confidentiality**: Permanent credentials, API tokens, and Docker daemon sockets are never exposed to the container environment.
5. **Recovery Fencing**: When a worker dies, runs are recovered through authoritative lease fences and quiescence verification without assuming process termination.
6. **No Host Fallback**: If Docker is unavailable or misconfigured, untrusted workloads fail closed. Host/in-process execution is never used as an automatic fallback.

---

## 2. Threat Actor & Attacker Profile

We model the attacker as an untrusted or adversarial workload running inside the execution environment:
- **Capabilities**:
  - Arbitrary code execution within the assigned process context (e.g. bash, node, python, compiled binaries).
  - Ability to attempt filesystem traversal (`..`, symlinks, hardlinks, alternate data streams).
  - Ability to spawn unbounded subprocesses (fork bombs).
  - Ability to flood standard output/standard error to exhaust buffers or host memory.
  - Ability to attempt network requests against host loopback (`127.0.0.1`, `localhost`, `172.17.0.1`, `host.docker.internal`).
  - Ability to probe for Docker daemon interfaces (`/var/run/docker.sock`, `\\.\pipe\docker_engine`).
  - Ability to inspect environment variables and process memory for leaked credentials.
  - Ability to attempt Linux capability abuse and privilege escalation (`setuid`, `CAP_SYS_ADMIN`, `CVE-2024-21626`).

## 3. Trust Boundaries

```
[ Untrusted Workload / Agent Code ]
                 │
                 ▼ (Boundary 1: Container User & Linux Capabilities)
[ Non-Root Container Context: UID 1000:1000, --cap-drop=ALL, no-new-privileges ]
                 │
                 ▼ (Boundary 2: Storage & Filesystem Isolation)
[ Read-Only Rootfs + /tmp (64m tmpfs) + Confined /workspace Bind Mount ]
                 │
                 ▼ (Boundary 3: Network Isolation)
[ Isolated Network Namespace: --network=none, No host loopback access ]
                 │
                 ▼ (Boundary 4: Daemon & Kernel Isolation)
[ Independent Rootless Daemon Validation + Cgroup v2 Limits: CPU, Memory, PIDs ]
                 │
                 ▼ (Boundary 5: Host OS & Host Filesystem)
[ Host Kernel & Host System: Protected from Traversal, Socket Access, Host Root ]
```

## 5. Defense-in-Depth Security Controls

1. **Non-Root Container User**:
   - Containers run as an unprivileged user (default `1000:1000`).
   - Root user (`UID 0`, `GID 0`, `root`) is rejected fail-closed at configuration and launch time.

2. **Rootless Daemon Verification**:
   - Distinguishes non-root container process from rootless Docker daemon.
   - Rootless daemon validation is authoritatively mandatory for `UNTRUSTED_WORKLOAD`, `ADVERSARIAL_WORKLOAD`, and `MULTI_TENANT_WORKLOAD`.
   - Daemons are independently inspected via `docker info` security options. When policy mandates rootless operation, daemons running as host root are rejected fail-closed.

3. **Capability Dropping & Privilege Escalation Prevention**:
   - `--cap-drop=ALL` strips all Linux capabilities.
   - `--security-opt=no-new-privileges` prevents `setuid` binaries from gaining elevated privileges.
   - Privileged mode (`--privileged`) is permanently disallowed.
   - Host namespace sharing (`--pid=host`, `--ipc=host`, `--net=host`) is permanently disallowed.

4. **Network Confinement**:
   - `--network=none` disables network interfaces inside the container, preventing egress, ingress, and local network exploration.

5. **Filesystem Confinement**:
   - `--read-only` root filesystem prevents modification of runtime binaries and libraries.
   - `--tmpfs=/tmp:rw,noexec,nosuid,size=64m` provides bounded, non-executable temporary storage.
   - Canonical workspace mount path verification rejects path traversal (`..`), symlinks, host root (`/`), user home, repository root, system directories (`/etc`, `/proc`, `/sys`, `/dev`, `C:\Windows`), and Docker sockets.
   - Sibling tenant isolation: Tenant A's container cannot mount Tenant B's workspace directory.
   - **Residual TOCTOU Limitation (E-10, E-12)**: Canonical path validation through `fs.realpathSync()` does not mathematically eliminate a race where a concurrent host process changes the filesystem or symlink between validation and Docker bind-mount creation. Canonicalization does not completely prevent TOCTOU attacks.

6. **Resource Caps**:
   - Memory ceiling (`--memory=256m`) prevents out-of-memory crashes of the host.
   - CPU quota (`--cpus=0.5`) limits CPU starvation.
   - PID limit (`--pids-limit=64`) stops fork bombs.
   - Max output limit (1 MB default) terminates stdout/stderr flooding.
   - Wall-clock timeout triggers physical container termination via `docker stop -t 2` followed by `docker kill`.

7. **Safe Failure & Recovery Semantics**:
   - Daemon disconnection during execution results in `TERMINATION_UNVERIFIED` / `EXECUTION_OUTCOME_UNKNOWN`.
   - The runtime never assumes an unobserved container stopped. Lease expiry recovery handles verification under quiescence.

## 8. Accepted Limitations & Verification Scope

### Accepted Limitations
1. **Windows Docker Desktop / WSL2 Rootful Daemon (E-02, E-03)**:
   - On Windows development environments running Docker Desktop with Linux containers, the daemon operates in rootful mode (`SecurityOptions` does not report `rootless`).
   - The runtime correctly fails closed with `ROOTLESS_VALIDATION_FAILED` for `UNTRUSTED_WORKLOAD`, `ADVERSARIAL_WORKLOAD`, and `MULTI_TENANT_WORKLOAD` unless running against a native Linux rootless daemon or using the mock command runner in automated tests.
2. **Filesystem Mount TOCTOU Race Condition (E-10, E-12)**:
   - Canonical path validation through `fs.realpathSync()` does not mathematically eliminate a race where a concurrent host process alters the filesystem or symlinks between validation and container launch.
3. **Container Image Tag vs Digest Pinning (E-18)**:
   - Default container images are referenced by tag (e.g., `alpine:latest`, `emerald-sandbox:latest`) rather than immutable SHA-256 digests unless explicit digests are specified in the mission policy.
