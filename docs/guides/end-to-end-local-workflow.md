# Emerald Agent Fabric — End-to-End Local Workflow Runbook & Guide (Milestone 2.20)

## 1. Overview & Operational Lifecycle

Emerald Agent Fabric implements a durable, governed, zero-cost, local-first runtime for executing autonomous software engineering tasks. Milestone 2.20 unifies the infrastructure layers developed in Milestones 2.16 through 2.19 into an end-to-end operational pipeline:

```
[ User Intent / CLI ]
        │
        ▼
[ 1. Durable Submission ] ────► Persists Task, Active Contract & CREATED Run in SQLite WAL
        │
        ▼
[ 2. Router Host ]        ────► Evaluates tree dependencies, applies concurrency caps, transitions CREATED ➔ QUEUED
        │
        ▼
[ 3. Worker Host ]        ────► Registers worker, acquires worker lease (LEASED), transitions ➔ RUNNING
        │
        ▼
[ 4. Governed Execution ] ────► Multi-turn loop: Context ➔ Model Proposal ➔ Policy Gate ➔ Governed Tool Execution
        │
        ▼
[ 5. Verification Latch ] ────► Evaluates Contract Verification Specifications (Exit codes, test suites, checks)
        │
        ▼
[ 6. Durable Completion ] ────► Transitions ➔ COMPLETED, releases lease, writes terminal event
        │
        ▼
[ 7. Inspection & Export ]────► Emits JSON evidence, inspects event streams, exports unified diff and manifest.json
```

### Architectural Separation
- **Router Host (`emerald router host`)**: Owns task dependency evaluation, tree cascading cancellation, and capacity admission into the queue. It never executes agent steps or touches workspace files.
- **Worker Host (`emerald worker`)**: Owns queue polling, worker lease acquisition, workspace binding, model inference coordination, governed tool dispatch, and latch verification.
- **Persistence (`SqliteStateStore`)**: Serves as the authoritative source of truth. All state changes occur in durable transactions with optimistic version checks and lease fencing.

## 2. CLI Command Reference

### 2.1 Durable Task Submission
Submits a governed task or operation to SQLite. Creates the database file if it does not yet exist.
```bash
emerald router submit \
  --db ./emerald.sqlite \
  --key "task-submission-key-001" \
  --task "Fix issue #42: Validate port boundaries in config.json" \
  --repo ./target-repo \
  --timeout-ms 300000 \
  --max-attempts 3
```
- `--key <string>`: Idempotency submission key. Re-submitting with the same key returns the existing run without duplicate records. Conflicting payload under an identical key fails closed with exit code 1.
- `--task <string>`: Natural language task description for agent reasoning.
- `--repo <path>`: Local repository directory containing the target codebase.

### 2.2 Starting the Long-Running Router Host
Continuously dispatches eligible tasks while enforcing concurrency ceilings and backoff on database contention.
```bash
emerald router host \
  --db ./emerald.sqlite \
  --max-concurrent 2 \
  --poll-interval-ms 1000 \
  --busy-backoff-ms 100 \
  --max-busy-backoff-ms 5000
```
- `--once`: Dispatches a single tick and exits (ideal for deterministic testing and cron triggers).

### 2.3 Starting the Worker Host
Continuously claims `QUEUED` runs and drives autonomous execution.
```bash
emerald worker \
  --db ./emerald.sqlite \
  --model-provider fixture \
  --workspace-root ./workspaces \
  --poll-interval-ms 1000 \
  --lease-ttl-ms 60000
```
- `--once`: Claims and processes at most one run, then cleanly terminates.
- `--model-provider <fixture|ollama|in-process>`: Model inference backend (see Section 4).
- `--workspace-root <dir>`: Directory where isolated execution workspaces are provisioned and recycled.

### 2.4 Inspecting Run Status & Event History
Inspects durable status, attempt counts, execution metrics, and the full cryptographic event ledger.
```bash
emerald inspect \
  --db ./emerald.sqlite \
  --run-id <run-id>
```
Output includes:

### 2.5 Exporting and Inspecting Artifacts
Inspects unified git diffs, changed files, and artifact manifests generated by completed runs.
```bash
emerald artifact show \
  --db ./emerald.sqlite \
  --run-id <run-id>
```
Produces:
- `manifest.json`: Metadata, timestamp, base commit, target commit, and changed file list.
- `patch.diff`: Git-compatible unified patch of all modifications performed by the agent.

## 3. SQLite WAL Configuration & Concurrency Policy

### 3.1 Write-Ahead Logging (WAL)
Emerald automatically initializes SQLite with Write-Ahead Logging (`PRAGMA journal_mode=WAL`) and normal synchronization (`PRAGMA synchronous=NORMAL`).
- Reads do not block writes; writes do not block reads.
- Atomic commits are guaranteed across runs, leases, actions, and event streams.

### 3.2 Concurrency Caps
- To prevent CPU thrashing and maintain stability on single developer machines, the Router Host enforces a strict concurrency ceiling (`maxConcurrentRuns`: 1 or 2).
- When in-flight tasks meet or exceed the cap, additional tasks remain in `CREATED` state until earlier runs reach a terminal state (`COMPLETED` or `FAILED`).

## 4. Local Model Execution Configuration

Emerald enforces a ₹0-cost constraint: execution relies exclusively on local, offline, or open-weight models without external proprietary API keys.

### 4.1 Deterministic Fixture Provider (`--model-provider fixture`)
Ideal for integration testing, deterministic CI verification, and offline test harnesses:
- Deterministically analyzes task objectives and workspace contents.
- Proposes valid sequence of governed tools (`read_file` ➔ reasoning ➔ latch verification).
- Fails closed on invalid commands without executing unauthorized operations.

### 4.2 Local Ollama Provider (`--model-provider ollama`)
Executes real local open-weight language models via a local Ollama daemon:
```bash
emerald worker \
  --db ./emerald.sqlite \
  --model-provider ollama \
  --model qwen2.5-coder:7b \
  --ollama-base-url http://127.0.0.1:11434 \
  --workspace-root ./workspaces
```
Requirements:
1. Local Ollama running (`ollama serve`).
2. Target model pulled (`ollama pull qwen2.5-coder:7b` or `deepseek-r1:8b`).
3. Model proposals must conform strictly to typed tool schemas (`read_file`, `write_file`, `search_code`, `git_diff`, `run_command`).

## 5. Crash Recovery & Lease Fencing Semantics

Emerald is architected around the core distributed systems invariant:
> *Never assume process restart implies success. Interrupted execution must be fenced, audited, and fail closed.*

### 5.1 Worker Lease Fencing
- Every run claimed by a worker holds an exclusive time-bounded lease (`leaseId`) and heartbeat deadline (`expiresAt`).
- If a worker crashes or hangs past its lease deadline, the sweeper (`coordinator.recoverExpiredRuns()` or `emerald recovery sweep`) revokes the expired lease and moves the run back to `QUEUED`.
- Any subsequent attempt by the stale worker process to commit changes or transition the run throws `LeaseLostError` and is rejected at the database boundary.

### 5.2 Zero-Cost In-Flight Resume Policy
- Emerald explicitly sets `safeToResume: false` during recovery of interrupted non-idempotent actions.
- Crashed or killed runs do not blindly resume in-flight mutations; instead, stale executions are transitioned to terminal `FAILED` state, protecting source repositories from duplicate non-idempotent corruption.

## 6. Troubleshooting & Diagnostics

| Symptom / Error | Root Cause | Remediation |
| :--- | :--- | :--- |
| `SQLITE_BUSY: database is locked` | High write concurrency across multiple workers or CLI invocations. | The Router Host automatically applies exponential backoff. Increase `--busy-backoff-ms` or reduce concurrency. |
| `LeaseLostError: Run '<id>' lease lost` | Worker process paused or exceeded its `lease-ttl-ms` heartbeat deadline. | Increase `--lease-ttl-ms` (e.g. `120000`) or inspect worker CPU saturation. |
| `VERIFICATION_FAILED` | Agent generated code failed contract verification specifications (e.g. non-zero exit code). | Inspect verification logs via `emerald inspect --db <file> --run-id <id>`. Inspect test failure in workspace. |
| `StagnationDetector: REPEATED_IDENTICAL_READ` | Agent model proposed identical file read repeatedly without progress. | Provide clearer task description in `--task` or verify the target file exists in the repository. |
