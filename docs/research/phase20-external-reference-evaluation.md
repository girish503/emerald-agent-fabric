## 1. Scientific Hypotheses

This research contract defines a controlled scientific experiment to evaluate:

> **H1**: A sufficiently capable external coding model can cross the capability boundary that the tested local CPU model set failed to cross, while Emerald's governance, execution, clean-room verification, and evidence architecture remain unchanged.

> **H2**: The dominant limitation observed in Phases 15–19 is model/inference capability rather than Emerald's execution/governance architecture.

Neither hypothesis is assumed to be true. The evaluation contract is designed to be capable of falsifying both:

- If an external reference model passes all verification gates without modifying Emerald's architecture, **H1 is supported and H2 is corroborated**.
- If a frontier-class external model also fails within Emerald's pipeline, or if failures are traced to governance or verifier defects, **H1 is falsified and H2 is refuted**, pointing to architectural or interface deficiencies within Emerald.

  The content field must contain the actual JavaScript source code.

  Do not output placeholders.
  Do not output Markdown.
  Do not output an explanation instead of code.

- **Target Fixture**: `src/math.js` (contains defective `add` returning `a - b`), `test/target.test.js` (asserts `add(2, 3) === 5`), `test/regression.test.js` (asserts `multiply` behavior preserved).

## 4. Gate Structure

The reference experiment executes through four sequential verification gates:

### Gate A — Model Response Feasibility
- **Maximum Response Ceiling**: 120,000 ms (explicitly enforced via `timeoutMs`).
- **Measurements**:
  - Request dispatch timestamp and response arrival timestamp
  - Latency: `durationMs`
  - HTTP / API status codes and errors
  - Token counts: `inputTokens`, `outputTokens`, `totalTokens` (where reported by provider)
  - Raw response byte size
  - Proposal JSON deserialization result
  - Structural proposal conformance
- **Pass Criteria**:
  - Valid HTTP 200 response received within 120s
  - Output text parses as valid JSON
  - Output conforms to `action_proposal` structured output schema
  - Correct discriminator branch (`isGoalReached: false` with valid tool proposal)
  - Valid registered tool name (one of 6 tools)
  - Valid, schema-compliant `inputPayload`
- **Gate A Failure Rule**: A premature `{"isGoalReached": true}` claim without preceding tool actions and verification constitutes an immediate Gate A failure.

### Gate B — Governed Execution
If Gate A passes, the full governed agent loop executes.
- **Measurements**:
  - Total model invocations
  - Valid proposal count vs invalid proposal count
  - Governance rejection count and stages (Stages 1–11)
  - Physical tool executions dispatched through `ToolExecutionGateway`
  - SQLite Action count and Attempt count
  - Workspace mutation evidence (tracked file modifications)
  - Recovery behavior following any governance feedback
  - Final loop terminal status
- **Pass Criteria**:
  - Agent performs inspection (`read_file` on `src/math.js`)
  - Agent executes physical repair (`write_file` on `src/math.js`)
  - Zero governance bypasses or security violations
  - Agent observes repair outcomes and proposes completion only after repair is made

### Gate C — Clean-Room Verification
If the model emits `isGoalReached: true`, the frozen Phase 14 `CleanRoomVerifier` executes in complete isolation:
- **Requirements**:
  - Materialize pristine baseline commit in isolated workspace
  - Baseline FAIL_TO_PASS test failure confirmed (`add(2,3)` fails)
  - Baseline PASS_TO_PASS regression test success confirmed (`multiply` passes)
  - Extract unified patch from agent workspace
  - Apply unified patch to pristine baseline
  - Patched FAIL_TO_PASS test execution must SUCCEED (exit code 0)
  - Patched PASS_TO_PASS regression test execution must SUCCEED (exit code 0)
  - Suite execution count > 0
  - Static scope audit: no modifications outside `src/math.js`
  - Clean-room container / directory safely disposed
- **Authority Invariant**: No model or external provider may declare itself verified. Only `CleanRoomVerifier` can produce authoritative verification proof.

### Gate D — Fourfold Completion
Final mission success requires the conjunctive satisfaction of the fourfold gate predicate:
$$\text{Success} \iff \text{TaskSatisfied} \land \text{VerificationPassed} \land \text{PolicySatisfied} \land \text{EvidenceComplete}$$
- `TaskSatisfied`: Model claimed completion after valid repair.
- `VerificationPassed`: `CleanRoomVerifier` passed with F2P=1.0 and P2P=1.0.
- `PolicySatisfied`: No capability violations, no path traversals, no lease fencing breaches.
- `EvidenceComplete`: Complete trace of Actions, Attempts, Events, Diffs, and Metrics persisted.

## 5. Deterministic Classification Taxonomy

Every experimental trial terminates in exactly one deterministic classification code:

| Classification Code | Domain | Description |
| :--- | :--- | :--- |
| `MODEL_SCHEMA_FAILURE` | Model | Output is unparseable JSON, malformed schema, or premature completion claim |
| `MODEL_CAPABILITY_FAILURE` | Model | Model trapped in loops, unable to sustain trajectory, or hallucinating arguments |
| `MODEL_CODING_FAILURE` | Model | Model produces incorrect code, syntax errors, or placeholder comments |
| `MODEL_RECOVERY_FAILURE` | Model | Model fails to correct behavior after receiving governance rejection feedback |
| `MODEL_VERIFICATION_FAILURE` | Model | Model claims completion but clean-room verification fails (F2P or P2P failure) |
| `PROVIDER_API_FAILURE` | Provider | External API returned HTTP 4xx/5xx or malformed provider response |
| `PROVIDER_TIMEOUT` | Provider | External provider exceeded 120s timeout ceiling |
| `AUTHENTICATION_FAILURE` | Provider | Missing, invalid, expired, or rejected API credentials |
| `RATE_LIMIT_FAILURE` | Provider | HTTP 429 or quota exceeded from external provider |
| `NETWORK_FAILURE` | Environment | Socket error, DNS failure, connection reset, or external network unreachable |
| `ENVIRONMENT_FAILURE` | Environment | Local host OOM, Docker daemon failure, or OS process crash |
| `GOVERNANCE_FAILURE` | Architecture | Emerald governance erroneously rejected a fully compliant, authorized proposal |
| `VERIFICATION_FAILURE` | Architecture | CleanRoomVerifier crashed or failed due to test harness defects |
| `UNKNOWN_FAILURE` | Unclassified | Unhandled anomaly not captured by above classifications |

### Precedence Rules
To prevent provider infrastructure failures from being misclassified as model capability failures:
1. `NETWORK_FAILURE` precedes `PROVIDER_TIMEOUT`
2. `AUTHENTICATION_FAILURE` and `RATE_LIMIT_FAILURE` precede `PROVIDER_API_FAILURE`
3. `PROVIDER_API_FAILURE` and `PROVIDER_TIMEOUT` precede all `MODEL_*` failures
4. `GOVERNANCE_FAILURE` and `VERIFICATION_FAILURE` precede all `MODEL_*` failures
5. `MODEL_SCHEMA_FAILURE` precedes `MODEL_CODING_FAILURE`
6. `MODEL_CODING_FAILURE` precedes `MODEL_VERIFICATION_FAILURE`

## 6. Three-Way Scientific Separation

The experiment report must maintain strict separation across three independent dimensions:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Model Capability                                                    │
│    - Did the model inspect before editing?                             │
│    - Did it construct valid tool arguments?                            │
│    - Did it sustain reasoning across observations?                     │
│    - Did it write correct, functional code without placeholders?        │
│    - Did it recognize when the goal was achieved?                      │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Provider Infrastructure                                              │
│    - Did the provider return responses within 120s?                    │
│    - Were API endpoints available and error-free?                      │
│    - Did the provider faithfully pass through JSON schemas?            │
│    - Were token counts and usage metrics accurately reported?          │
├────────────────────────────────────────────────────────────────────────┤
│ 3. Emerald Architecture                                                │
│    - Did ProposalValidator correctly evaluate schemas?                 │
│    - Did PolicyEvaluator enforce least privilege?                      │
│    - Did ToolGateway sandbox and isolate execution?                    │
│    - Did CleanRoomVerifier independently verify the patch?             │
│    - Did StateStore persist full audit trails?                         │
└────────────────────────────────────────────────────────────────────────┘
```

These three domains must never be collapsed into a single ambiguous pass/fail metric.

## 8. Provider Selection Criteria

Selection of an external reference provider must be based on objective criteria, not brand reputation:

1. **Coding Capability**: Documented strong performance on public SWE benchmarks (SWE-bench Verified >40%).
2. **Structured Output Reliability**: Native support for strict JSON Schema output matching `action_proposal`.
3. **Tool-Use Reliability**: High fidelity in function calling and closed-schema parameter adherence.
4. **Latency**: Typical response latency under 15 seconds for 2k–4k context tokens.
5. **API Stability**: Documented, versioned HTTP API with formal backward-compatibility policies.
6. **Cost Transparency**: Clear per-token pricing with no opaque minimum commitments.
7. **Privacy & Data Retention**: Zero-data-retention or enterprise privacy options ensuring source code is not retained for model training.
8. **Context Capacity**: Minimum 32k context window to comfortably handle workspace contexts.
9. **Deterministic Evaluation Capability**: Support for `seed` and `temperature: 0.0` to maximize evaluation reproducibility.
10. **Port Compatibility**: Ability to integrate directly via standard HTTPS behind `ModelProviderPort` without mandatory heavyweight SDK dependencies.

## 9. End-to-End Success Criteria

The strongest useful success condition for the future external reference experiment is defined as:

1. **Gate A PASS**: Valid tool action proposal generated within 120s
2. **Physical Workspace Mutation**: At least one file modified via `write_file`
3. **Task-Directed Repair**: Defect in `src/math.js` repaired such that `add(2, 3)` returns `5`
4. **Preserved Regression Behavior**: Existing `multiply` functionality unaltered
5. **Zero Unauthorized Actions**: No access outside workspace, no illegal tools
6. **Correct Completion Behavior**: `isGoalReached: true` proposed only after repair
7. **Clean-Room Verification PASS**:
   - `FAIL_TO_PASS = 1`
   - `PASS_TO_PASS = 1`
   - `SUITE_EXECUTION_COUNT > 0`
   - `STATIC_SCOPE_AUDIT = PASSED`
8. **Evidence Complete**: Complete relational SQLite records and verified JSON evidence bundle
9. **Fourfold Gate Predicate**: Evaluates to `TRUE`

A model that generates valid syntax but incorrect logic fails. A model that fixes the bug but breaks regression tests fails. A model that edits code but fails clean-room verification fails.

## 10. Threats to Validity

1. **Single Coding Task**: The math repair task tests localized unit-level bug repair; it does not measure multi-module architectural reasoning.
2. **Limited Model Sample**: One external reference model does not characterize all cloud LLMs.
3. **Parameter Count Is Not Capability**: High parameter count does not guarantee compliance with Emerald's strict governance.
4. **Different Model Families**: Local models (Llama, Qwen, Gemma) may respond differently to prompt structures than frontier models (GPT, Claude, Gemini).
5. **Quantization Differences**: Local models ran at Q4_K_M; cloud models run at full or higher-precision quantization.
6. **CPU Hardware Specificity**: Local baseline latency is tied to the Intel i3-N305 processor; comparisons reflect current developer hardware.
7. **Single Local Host**: Host OS scheduling and background activity affect local measurements.
8. **External Provider Nondeterminism**: API inference may exhibit non-zero variance even at temperature 0.0.
9. **Provider Model Version Drift**: Cloud models undergo silent updates; evaluations must pin explicit snapshot version identifiers.
10. **Network Latency Variance**: Internet routing introduces jitter not present in local loops.
11. **Temperature Zero Non-Determinism**: Batch parallel processing can cause subtle numerical divergence.
12. **Narrow Benchmark Scope**: Success on this task is a necessary milestone, not general proof of software engineering autonomy.
13. **Generalization Boundary**: Autonomous coding across real-world repositories involves far broader complexities than single-function repair.
