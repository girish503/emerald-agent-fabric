# Phase 35A — Existing Cryptography Audit
## Audit of Cryptographic Facilities, Signing Semantics, and Authority Boundaries

---

### 1. What Exact Bytes Should Be Signed?
The signature must cover a deterministic, collision-resistant cryptographic representation that transitively protects the complete accepted evidence bundle.
- The signed payload is defined as:
  ```json
  {
    "bundleId": "<bundleId>",
    "formatVersion": "emerald-evidence-bundle-v1",
    "provenanceRoot": "<provenanceRoot>",
    "schemaVersion": 1
  }
  ```
- The exact bytes signed are the UTF-8 bytes of `canonicalJsonStringify(signingPayload)`.
- The `signedContentDigest` is `sha256Hex(canonicalJsonStringify(signingPayload))`.
- **Transitive Protection Proof**:
  - `bundleId` is the SHA-256 digest of the canonical serialization of all bundle contents (`run`, `contract`, `checkpoints`, `events`, `actions`, `attempts`, `supervisorEvidence`, `verificationEvidence`, `verificationResults`, `terminalState`, `provenance`).
  - `provenanceRoot` is the SHA-256 digest of the 5 subsystem Merkle roots (`contractHash`, `eventRoot`, `checkpointRoot`, `attemptRoot`, `verificationRoot`).
  - The ingestion gateway independently recomputes `bundleId` and `provenanceRoot` from the raw bundle contents before verifying the signature.
  - Any alteration to any file, action, attempt, event, or outcome produces a different `bundleId` or `provenanceRoot`, immediately invalidating either the structural recomputation or the Ed25519 signature.

---

### 2. Should Signing Cover bundleId?
**YES.** `bundleId` is the primary cryptographic content commitment over the entire bundle. Binding `bundleId` in the signed payload ensures that the signature is inextricably bound to the exact content of the mission.

---

### 3. Should Signing Cover provenanceRoot?
**YES.** `provenanceRoot` represents the root of the Merkle subsystem integrity trees. Signing both `bundleId` and `provenanceRoot` provides defense-in-depth across the execution subsystems.

---

### 4. How Is Signature Metadata Represented?
The signature is represented by an explicit `EvidenceSignature` structure:
```typescript
export interface EvidenceSignature {
  readonly algorithm: "Ed25519";
  readonly keyId: string;
  readonly publicKeyFingerprint: string;
  readonly signature: string; // 64-byte hex string (128 hex chars)
  readonly signedContentDigest: string; // 32-byte hex string (64 hex chars)
}
```
This is placed on the evidence bundle as `bundle.signature?: EvidenceSignature`.
By keeping `signature` outside `EvidenceBundleContent`, `computeBundleId` strips `signature` during recalculation, preventing circular dependency while allowing the signature to accompany the bundle as a single self-contained JSON document.

---

### 5. Where Should Public Keys Be Configured?
Public keys are configured in a local, offline `TrustedKeyring` class implementing a key registry:
- Statuses: `TRUSTED`, `REVOKED`.
- Public keys can be provided as SPKI PEM strings, SPKI DER buffers, or Node.js `KeyObject` instances.
- Zero network I/O, zero external PKI servers, zero certificate authorities, zero blockchain dependencies.

---

### 6. How Should Key IDs Be Represented?
`keyId` is a non-empty string identifier (e.g. `"host-alpha-worker"`, `"supervisor-key-2026"`).
- `keyId` is purely routing metadata.
- Verification resolves `keyId` against the local `TrustedKeyring` to obtain the trusted public key.
- If a producer claims `keyId === "alice"` but provides a signature generated by `bob`, or if the key in the keyring does not match the signature, verification fails. Authority resides in the trusted key, not the declared string label.

---

### 7. What Happens to Unsigned Legacy Bundles?
Legacy Phase 33 and Phase 34 bundles do not possess a `signature` property:
- Ingestion supports an explicit policy for legacy bundles:
  - If `allowUnsignedLegacy === true` (default in backward-compatible mode): Unsigned bundles that satisfy schema, bundleId, provenanceRoot, and replay verification are classified with:
    - `integrityValid = true`
    - `signatureStatus = "UNSIGNED_LEGACY"`
    - `authorityStatus = "NOT_ESTABLISHED"`
  - If `allowUnsignedLegacy === false` (strict mode): Unsigned bundles are quarantined with reason code `UNSIGNED_BUNDLE_REJECTED`.
- Legacy Phase 10H and Phase 33/34 test artifacts remain valid and untouched.

---

### 8. How Should Invalid Signatures Be Classified?
The ingestion gateway classifies invalid signatures into deterministic failure reason codes:
- `UNKNOWN_SIGNING_KEY`: The declared `keyId` is not registered in the keyring.
- `REVOKED_SIGNING_KEY`: The declared `keyId` is registered but marked `REVOKED`.
- `INVALID_SIGNATURE`: The Ed25519 cryptographic verification failed (tampered content, wrong key, truncated/mutated signature bytes).
- `INVALID_PUBLIC_KEY`: The key registered in the keyring or fingerprint is malformed or invalid.
- `INVALID_SIGNATURE_PAYLOAD`: Signature metadata algorithm is not `"Ed25519"` or required signature fields are missing.
- `UNSIGNED_BUNDLE_REJECTED`: The bundle is unsigned in a strict verification environment.

---

### 9. Can Signature Verification Remain Completely Offline?
**YES.**
Node.js standard library `node:crypto` provides native Ed25519 verification via:
```typescript
crypto.verify(null, payloadBuffer, publicKey, signatureBuffer);
```
This operates purely in memory with zero network sockets, zero DNS requests, zero disk I/O to remote systems, and zero model inference.
